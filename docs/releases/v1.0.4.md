# v1.0.4 - Archive Symlink Hardening and Dependency Refresh

## Summary
Fixes a privilege-escalation path in archive mode: the v1.0.2 containment check
kept the archive *path string* under `SAVE_PATH`, but `cp -f` / `chmod 644`
still followed a symlink planted at the destination name. Because the script
runs as root and `SAVE_PATH` is typically a user-writable share, anyone who
could write to that share could redirect the daily write onto an arbitrary
root-owned file. The archive step now refuses symlinks, stages the copy where
share writers cannot reach it, fails closed on any error, and re-checks the
destination after the final rename. Also refreshes the few pinned tools that
had newer final releases.

## Why This Change
- Archive filenames are public and predictable (`YYYYMMDD - title - credit.jpg`
  from Bing's API plus the documented sanitization rules), so a share writer
  can pre-create today's name as a symlink to e.g. `/etc/synoinfo.conf` or
  `/etc/shadow`.
- `ensure_archive_within_save_path` only `realpath`ed the parent directory, so
  the check passed and the root Task Scheduler run overwrote the link target
  with JPEG bytes and mode `644`.

## What Changed

### 1. Product script (`bing_wallpaper_auto_update.sh`)
- Added `reject_archive_symlink`: fails closed if `ARCHIVE_FILE` is a symlink
  (`test -L`) or exists as anything other than a regular file.
- Added `archive_staging_root` + `write_archive_file`: the file is staged in
  a private `mktemp -d` directory at `SAVE_PATH`'s mount point (`/volumeN` on
  DSM) — the same filesystem, but *outside the share*. Staging anywhere
  inside the share cannot be made safe: a share writer can unlink or replace
  a root-owned staging file or empty directory before `cp` opens it, and on
  DSM a `0700` directory created inside a share still inherits the share's
  Windows ACL, so POSIX-mode checks prove nothing. The mount point is
  accepted only when it is a volume root by shape (`/` or `/volumeN`) and
  owned by us with no group/other write bit — POSIX mode alone cannot tell a
  volume root from a share that is its own mount (an unlocked encrypted
  share is an ecryptfs mount at `/volumeN/<Share>`, a USB share is often
  the device mount, and both are root-owned `755` while SynoACL still grants
  share writers access). Otherwise the run fails closed with a message
  naming the requirement. `cp`/`chmod` happen at the volume root,
  untouchable.
- Added `place_archive_file`: the staged file is hard-linked into place with
  `ln -n`. `link(2)` never follows a symlink at the destination and fails if
  anything exists there, so a symlink swapped in after
  `reject_archive_symlink` is refused rather than followed; `-n` keeps `ln`
  from descending into a symlinked directory. The result is then confirmed
  to be our regular file. Every step fails closed and removes the staging
  directory on error (previously a failed write still logged success and
  exited 0).
- `archive_image` now calls these helpers instead of `cp -f` + `chmod` on the
  destination directly. Happy-path behavior and the archive filename format
  are unchanged. Script header version bumped to 1.0.4.

### 2. Tests (`tests/run_kcov_cases.sh`)
- New component-lane case `archive_symlink_destination`: plants a symlink at
  the mock's predicted archive name pointing at a sentinel file outside
  `SAVE_PATH`, runs the script, and asserts it exits non-zero, the sentinel
  is untouched, the symlink was neither followed nor replaced, and no staging
  directory was left behind.
- New `tests/archive_write_cases.sh` (component lane, under kcov): sources the
  real script and drives `write_archive_file` / `place_archive_file`
  through the branches the end-to-end mock cannot reach — an unusable
  staging root (missing; a share-shaped mount such as `/volume1/Share`; a
  volume root writable by others — via a PATH-level `df` stub — plus a
  positive check of a root-owned `755` volume root), copy failure with staging cleanup, hard-link placement refusal when
  a directory appears at the destination, the non-regular-file branch of
  `reject_archive_symlink`, and same-day re-run replacement. These validate
  each check against representative directories; they do not perform a
  live swap of the staging path mid-write.
- `tests/verify_dsm_mock.sh` now also requires the archived file to be a
  regular non-symlink file and that no `@bing_archive.*` staging directory
  remains after a successful run.

## Notes
- Residual: a *real directory* created at the destination between
  `reject_archive_symlink` and `ln` receives the hard link inside it (inside
  the share — it cannot escape `SAVE_PATH`, and the basename is ours). This
  is detected by the post-link check and fails the run; the stray file is
  left for the administrator to remove.
- Requirement: `SAVE_PATH` must live on an internal volume whose root
  (`/volumeN`) is root-owned and not group/other-writable. **Encrypted
  shared folders and USB/eSATA shares are not supported for `SAVE_PATH`**:
  they are their own mounts, and SynoACL grants share writers access to
  them regardless of POSIX mode, so there is no private place on their
  filesystem to stage. Archiving fails with a clear error in that case
  rather than staging somewhere a share writer can reach.
- Recommended deployment: point `SAVE_PATH` at a folder only administrators
  can write to rather than a broadly shared one.
